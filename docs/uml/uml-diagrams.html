Fig. 1 — Class diagram (28 classes, 2 interfaces, 2 utility modules) Source: backend/app/
Composition App creates and owns the database, bus, processor, analytics, alert engine and WebSocket hub — they are constructed in its __init__ and destroyed with it.
Realization Six collectors realize the Collector interface, so adding a data source needs no change to App — it only implements poll().
Strategy pattern MemoryBus and KafkaBus are interchangeable implementations of MessageBus; the system falls back to the in-memory queue when Kafka is unavailable.
Dependency Dashed arrows mark object creation: Processor produces Mention objects, AlertEngine produces Alert objects.

Fig. 3 — Component diagram with provided / required interfaces 4 external APIs · 5 collectors · 1 shared model instance
Decoupling Collectors never call the NLP engine directly — they publish to the message bus, so a slow API or a burst of comments cannot stall classification.
Batching The processor consumes up to 32 messages per batch, which is what keeps inference at ~9 ms per comment on CPU.
Shared database SQLite is the integration point between processing and analytics; the analytics engine reads the same store the processor writes to.
Push channel Alerts reach the dashboard through the WebSocket hub, so the UI updates without polling.
For your viva: the three diagrams answer three different questions — the class diagram shows what the system is made of, the object diagram shows what it looks like while running, and the component diagram shows how the parts are deployed and connected.
